# Учебник владельца системы

> Для того, кто ведёт Team OS (обычно — тот, кого раньше спрашивали обо всём).
> `GUIDE.md` — для команды, этот файл — про твою рутину и про то, что ломается.
> Таблицу инцидентов ведите сами: каждая строка — реальный случай.

## Ментальная модель

Три слоя + агент (см. `GUIDE.md`). Слой знаний говорит «как обещано», код —
«как есть». При расхождении прав код; расхождение — повод поправить репо, а не
спорить.

## Твоя неделя

| Когда | Что | Сколько |
|---|---|---|
| Каждый день | Прочитать дайджест (если подключён агент), разобрать «требует ответа» | 5–10 мин |
| Когда спрашивают лично | Не отвечать текстом — переадресовать агенту в том же треде | 0 мин |
| Раз в неделю | Ревью brain-sync PR: что система выучила; мёрж или правка | 15 мин |
| На регулярной встрече | 5 минут вердиктов agree/disagree по pending-решениям | 5 мин |
| Раз в месяц | Посчитать «сколько вопросов ответило репо, а не я»; разобрать `QUESTIONS.md` | 20 мин |

## Почему доки не могут врать

`brain/claims.yaml` привязывает утверждения доков к константам и файлам кода.
`brain/scripts/check_drift.py` в pre-commit хуке сверяет их: код разошёлся с
доком — коммит падает со списком «код говорит / в доке нет». Код не выкачан —
чекер пишет SKIPPED и не делает вид, что проверил.

Перед выводами «в коде такого нет» или «этот файл мёртв» — `git pull` в клоне
кода. Устаревший клон даёт уверенные и ложные выводы.

## Что уже ломалось

> Заполняйте по мере инцидентов: симптом → причина → фикс. Пример (Acme):

| Симптом | Причина | Фикс |
|---|---|---|
| Агент уверенно назвал статус записи, которого нет | статусы в доке писали по памяти | статусы перенесены в claim-секцию `brain/product/object-model.md` |
| `last_reviewed` свежий, а факт устарел | конвейер агента сам обновлял дату | боты ставят `bot_updated`, `last_reviewed` — только человек |
