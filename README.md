# team-os-knowledge — репозиторий знаний команды (шаблон)

**Команда спрашивает репозиторий, а не тебя.**

Каждый день тебя спрашивают одно и то же: «есть ли у нас такая фича?», «какой у
неё статус?», «как это работает?», «а что бы ты решил?». Этот шаблон выносит
ответы из твоей головы в git-репозиторий, которому можно доверять: у каждого
факта есть источник и владелец, утверждения о коде сверяются с кодом при каждом
коммите (врущая дока не проходит хук), а решения принимаются по датированным
принципам, выросшим из реальных эпизодов. Читают репо люди и агенты — Claude
Code, Codex или бот в чате — и отвечают с цитатой вместо тебя.

Структура извлечена из прод-системы автора и обезличена. Все примеры — выдуманный
сервис онлайн-записи **Acme**: при наполнении замените их своими.
Методика и часть шаблонов — Team OS Toolkit (MIT), автор Bayram Annakov: https://github.com/BayramAnnakov/team-os-toolkit

## Три слоя + агент

| Слой | Отвечает на вопрос | Файлы | Что держит его честным |
|---|---|---|---|
| **1. Знания** | как что работает, кто за что отвечает, есть ли фича | `CLAUDE.md`, `product/` | frontmatter `owner / tier / last_reviewed`, граница доверия |
| **2. Brain** | какие на самом деле статусы, сущности, термины | `brain/` | `claims.yaml` + `check_drift.py` в pre-commit |
| **3. Решения** | как мы решаем | `decisions.md`, `skills/decide-like-team/` | вердикты agree/disagree на встрече |
| **Агент** | голос системы в чате, работа по расписанию | `soul.md`, `robin/duties.md` | ответы только с источником; алерт, если duty упала |

Сам агент (бот + таймеры) — отдельный репо
[`team-os-agent`](https://github.com/slavkkoo/team-os-agent). Этот репо — его память.

## Круговорот знаний

```
Чаты команды и клиентов ──▶ Дайджесты (duty 1) ──▶ память «что я пропустил»
        │                        │
        │                        ▼
        │                Brain-sync PR (duty 2) ──▶ product/, brain/now.md
        │                        │
        ▼                        ▼
  Разбор решений ──▶ decisions.md (proposed) ──▶ вердикт на встрече (duty 3)
                                 │                        │
                                 ▼                        ▼
                     skills/decide-like-team       ratified-принципы
                                 │
                                 ▼
     Вопрос тиммейта ──▶ агент ──▶ ответ из репо + сверка с кодом
                                 │       (drift-чекер не даёт докам врать)
                                 ▼
                 QUESTIONS.md (не ответили) ──▶ PR с пополнением
```

Чаты становятся дайджестами, дайджесты — знаниями, знания — ответами, споры —
принципами, а вопросы без ответа — задачами на пополнение.

## Красное демо: доки не могут врать

`brain/claims.yaml` привязывает списки в доке к константам в коде. Из коробки
код — `examples/demo-code`, поэтому хук работает сразу после clone:

```bash
./scripts/setup.sh                       # хуки + проверки: 3 ok
# «разработчик переименовал статус, а доку не обновил»:
sed -i.bak 's/"no_show"/"missed"/' examples/demo-code/booking/status.py && rm examples/demo-code/booking/status.py.bak
git commit -am "rename status"           # коммит падает
git checkout examples/demo-code          # вернуть как было
```

Реальный вывод хука:

```
Team OS: drift-чекер
Код: examples/demo-code (code_root в claims.yaml)
FAIL     booking-status-values: в доке нет значений, которые есть в коде
         код говорит: cancelled, completed, confirmed, missed, pending
         в доке НЕТ:  missed  -> допиши в brain/product/object-model.md
WARN     booking-status-values: в доке есть значения, которых нет в коде: no_show (удалить из brain/product/object-model.md?)
ok       notification-channels
ok       booking-model-pointer

Итог: 2 ok, 1 failed, 0 skipped из 3.

Коммит отклонён: доки разошлись с кодом (см. FAIL выше).
```

Так же падает коммит, если в `notifications/channels/` появился новый канал, а
док о нём молчит, или если `booking/models.py` переехал. Код не выкачан
(`CODE_ROOT` не найден) — чекер честно пишет `SKIPPED ... НЕ проверены` и не
мешает коммиту; с `DRIFT_STRICT=1` (для CI) SKIPPED тоже роняет проверку.

Свой код: `CODE_ROOT=~/code/acme` в `.env` (или `code_root:` в `claims.yaml`),
свои клеймы — по шапке `claims.yaml`, `examples/` удалить.

## Как автор этим пользуется

- **Тиммейт спрашивает лично «есть ли у нас X?»** Я не отвечаю текстом, а тегаю
  агента в том же треде. Он отвечает из `product/features.md` с цитатой и
  указателем, где смотреть живой статус. Ответ с источником в общем треде — и
  есть демонстрация, которая продаёт систему лучше анонса.
- **Спор «а система так умеет?»** решается не мнениями: агент смотрит brain и
  код, а если доки и код разошлись — показывает обе версии.
- **В коде появился новый статус.** Коммит в репо знаний падает, пока кто-то не
  допишет статус в `brain/product/object-model.md`. Агент никогда не назовёт
  статус, которого нет.
- **«Делаем X или Y?»** Спрашивающий сначала пишет свою рекомендацию,
  `decide-like-team` цитирует принципы и показывает, где расходятся причины.
  Эпизод попадает в лог; на еженедельной встрече я ставлю agree/disagree за
  5 минут. Disagree чинит принцип.
- **Понедельник.** Агент присылает brain-sync PR: новый `now.md`, термины
  недели, кандидаты в принципы. Я ревьюю и мёржу — в основную ветку сам агент
  не пишет.
- **Раз в месяц** смотрю `QUESTIONS.md` и лог агента: сколько вопросов закрыло
  репо, сколько ушло ко мне, чего не хватает.

## Порядок внедрения

Порядок важен: агент без репо знаний — просто чат-бот.

1. **M0 — один вопрос.** Выберите самый частый повторяющийся вопрос к вам.
   Заполните `CLAUDE.md` и ровно столько `product/`, чтобы на него ответить.
   Откройте свежую сессию агента в репо и задайте вопрос: ответ должен прийти
   **из репо, с цитатой файла**.
2. **Покажите одному тиммейту.** Не анонс всей команде, а один реальный ответ
   там, где этот человек его увидит. Это M1.
3. **Brain.** Подключите код (`CODE_ROOT`), перенесите статусы и сущности в
   claim-секции, убедитесь, что чекер умеет краснеть.
4. **Решения.** Намайните 5–10 принципов из реальных эпизодов в
   `decisions.md`, начните 5-минутные вердикты на встрече.
5. **Агент.** `soul.md` + `robin/duties.md` → разверните
   [`team-os-agent`](https://github.com/slavkkoo/team-os-agent): ответы в чате,
   дайджест, brain-sync PR, напоминание о pending-решениях.

## Правила адопции

- **Адопция следует за ценностью, а не за анонсом.** Один настоящий ответ
  важнее презентации системы.
- **Отвечайте переадресацией.** Спросили то, что знает репо, — тегните агента
  или дайте ссылку на файл, а не пишите ответ сами.
- **5 минут вердиктов на регулярной встрече.** Команда видит, как её споры
  становятся принципами. Ревьюер brain-sync PR — по очереди, не только вы.
- **Поправки должны что-то менять.** Тиммейт сказал «агент ошибся» — через
  неделю ответ должен быть другим. Люди пользуются тем, что реагирует на их
  правки.
- **Мерьте одно число:** сколько вопросов за месяц ответило репо, а не вы.

## Граница доверия

Полный список — в [`CLAUDE.md`](CLAUDE.md). Коротко: в репо никогда не
попадают зарплаты, персональные данные клиентов, коммерческие условия в цифрах
(только указатель на систему-источник), секреты и «живые» статусы (только
датированный снапшот).

## Что можно добавить

Всё это можно добавить — в шаблон не вошло, потому что сильно зависит от
вашего стека.

- **Указатели на Notion и трекер с программной привязкой.** Зачем: агент
  показывает живой статус задачи, а не снапшот. Внимание: в репо по-прежнему
  только ссылки и датированные снапшоты; живое значение агент читает из API в
  момент ответа и называет источник.
- **Встречи и транскрипция.** Зачем: решения со встреч попадают в
  `decisions.md` без ручного пересказа. Внимание: согласие участников на
  запись; транскрипты в репо не кладутся — только выжимки решений со ссылкой.
- **Eval-харнесс.** Зачем: понять, помогает ли brain (протокол —
  `brain/evals/knowledge-impact.md`). Внимание: LLM-судья завышает
  «галлюцинации», а hold-out из той же партии, на которой правили промпт,
  льстит — берите свежую неделю и ревьюйте спорные вердикты вручную.
- **Обучение на тикетах поддержки.** Зачем: проверенные ответы операторов
  становятся `product/tickets/*.md`. Внимание: PII клиентов маскировать до
  того, как тикет попадёт к агенту; находки — только через PR; противоречия
  «оператор сказал X, код показывает Y» — человеку на вердикт.
- **CI-проверка в PR.** Зачем: локальный хук обходится `--no-verify`. Тот же
  `check-frontmatter.sh --all` и `check_drift.py --strict` в CI, с доступом к коду.
- **Детектор устаревших фактов.** Зачем: найти факты, у которых код по
  указанным путям менялся после `last_reviewed`. Внимание: это кандидаты на
  ревью, не автоматические правки.
- **Ambient-контекст в группах** — агент отвечает с учётом последних сообщений
  треда; делается в `team-os-agent`.

## Грабли

Уроки прода, за каждый заплачено.

- **Устаревший локальный клон даёт ложные выводы.** Выводы «этот файл мёртв» и
  «этого значения в коде нет» по отставшему клону оказывались неверными.
  `git pull` (и в репо знаний, и в `CODE_ROOT`) — перед любыми выводами.
- **Конвейеры, пишущие в основную ветку, — источник непроверенного «канона».**
  Автоматические конвейеры агента пушили знания в основную ветку без ревью, а
  «авто-ревью» на деле смотрело не тот дифф. Правило: только ветка + PR, у
  каждого конвейера — своя зона путей.
- **`last_reviewed` ставит только человек.** Когда боты обновляли дату сами,
  она перестала значить «человек проверил». Боты ставят `bot_updated`.
- **Большие файлы-свалки дорого читать агенту.** Один огромный FAQ на сотни
  ответов стоил десятки тысяч токенов на каждый вопрос. Разбивайте по разделам
  (`product/tickets/<тема>.md` + `INDEX.md`), один файл — одна тема.
- **SKIPPED ≠ проверено.** Если чекер не видит код, он должен сказать это
  вслух, а не печатать «всё ок». Иначе зелёный хук на машине без кода создаёт
  ложное доверие.
- **Статус в доке гниёт за неделю.** Только снапшот с датой + ссылка на
  систему, где живёт актуальное.
